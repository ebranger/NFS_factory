This is a list of things that could be improved.

Check that the polynomials match the input number. At currently I assume that this check is done by the python driver.

A Linux build (CMake). The code has fallbacks for the Windows-specific parts (free host memory, file positions), but the
binary relation files are read with fread there, without the read-ahead of the Windows build, and it has not been built or tested.

The 3LP candidate file (3lp: save) holds a in 32 bits, as the .bin format, so the candidates of relations with |a| of 2^31 or
more (from .ab or text files) are skipped and counted. With 3lp: auto they are checked. A candidate format with a 64-bit a
would keep them.

The other side's factor lists for .ab files: a batch check of the norms against the primes up to 2^28 (other_stage), with the
cofactors of norms with three or four larger primes factored apart from the rest. With nothing else on the GPU, 4 SNFS-240 files
took 46 s; 57 s with the norms factored by Pollard rho alone, and 37 s with no other side at all. What is left is mostly the rho
for the parts of the norms below 2^28, with the leaves. A second tree at 2^26 would split those (rho on 100,000 of them took 0.41 s,
and 0.29 s for the parts below 2^26 and between 2^26 and 2^28), about 1.6 s of the 46, but needs a stage within the stage. One walk
per thread instead of a warp per norm was tried, and was not faster (the threads of a warp diverge). The prime product of that
check takes about 8 s to set up, which only matters for short runs. The CPU build factors the norms on the CPU (a one-thread
SNFS-220 run was about 30 % slower than from the .bin file).

The thread of the checks now mostly waits for k_rho (Pollard rho on the two large prime cofactors, a thread each, about 240 per
SNFS-240 batch). A warp per cofactor (32 walks) was tried and was not faster.

A validating converter to .ab (finding the right a for the relations of old .bin files whose |a| is 2^31 or more, which needs the
polynomial) exists outside the repository; Utilities\RelationsToBinaryFormat converts without checking.

The 3LP second stage runs in the thread that checks the batches of the first stage, which waits for it, and the candidates in
an unfinished second stage batch are not part of the resume position: if a run is interrupted, they are lost.

Batch checking with early abort: a first batch against the primes up to about 2^20 only (a much smaller tree), and the full
check only for the few values whose remaining part can still be smooth. Perhaps 15-25 % faster, but it loses some relations,
and the best split depends on parameters that change during a factorization.

GPU transform kernels: they are limited by latency (registers, barriers between the passes), not memory bandwidth. Passes of
4 levels with 16 elements per thread would need fewer barriers, at the cost of registers. A few percent at most.

The plan of the integer NTT (number of primes and transform length) is chosen with a cost model of the CPU transforms. On the
GPU the CRT combine is a larger part, and grows with the square of the number of primes.

The prime product of the 3LP second stage (all primes below 2^lbp) takes about 1.3 s to set up on the CPU (the root tests of
28 million primes). Only noticeable on short runs.

On the CPU still: the polynomial values (about 2 ms per batch per tree thread), the check of the saved factor lists of the
relations found, relation values of more than 256 bits, other side norms of more than 256 bits, and tinyqs.

With -rels, a run stops after the batches in progress, so it finds a few more relations than asked for, more with a larger
pipeline.
